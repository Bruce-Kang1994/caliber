# PM能力评估框架

## 一、框架总览

### 1.1 设计原则

1. **岗位导向**：不同方向的PM，评估维度和权重不同
2. **证据驱动**：每个评分必须基于用户的真实经历，不是自我感觉
3. **升级式表达**：诊断语言是"基于长板如何补短板"，不是"你哪里不行"
4. **可行动**：每个短板都附带具体的提升路径

### 1.2 评估维度总表（15个维度，5大类）

| 类别 | 维度 | 说明 |
|------|------|------|
| **产品硬能力** | ① 需求分析与定义 | 能否从业务/用户中提炼清晰的需求，写出可执行的PRD |
| | ② 产品设计能力 | 用户旅程、信息架构、交互逻辑的设计水平 |
| | ③ 系统架构理解 | 能否设计多模块/多系统协同的产品方案 |
| | ④ 从0到1能力 | 有无从想法到上线的完整闭环经验 |
| | ⑤ 数据驱动决策 | 是否有用数据发现问题、验证假设、指导迭代的习惯 |
| **业务能力** | ⑥ 业务问题拆解 | 能否把模糊的业务问题结构化，找到核心卡点 |
| | ⑦ 商业化能力 | 定价策略、变现模型、LTV/CAC等商业思维 |
| | ⑧ 增长能力 | 获客、激活、留存、变现的实战经验 |
| **AI专项能力** | ⑨ AI产品设计 | 能否设计AI-native的产品方案（不只是加个AI功能） |
| | ⑩ AI技术理解 | 对模型能力边界、Prompt工程、AI架构的理解程度 |
| | ⑪ AI工具应用 | 用AI工具提升自身工作效率的实战程度 |
| **软能力** | ⑫ 用户研究 | 访谈设计、洞察提炼、需求验证的能力 |
| | ⑬ 项目管理与协作 | 跨部门推动、优先级决策、资源协调 |
| | ⑭ 自我认知与表达 | 能否准确认知自身能力并清晰表达经历价值 |
| **出海专项** | ⑮ 跨文化与本地化 | 对目标市场的文化理解、本地化产品设计能力 |

## 二、岗位权重配置

不同目标岗位，各维度的权重不同。权重决定了评估报告中哪些维度被重点展示。

### 2.1 权重分配表

| 维度 | B端PM | C端PM | AI PM | 增长PM | 数据PM |
|------|-------|-------|-------|--------|--------|
| ① 需求分析与定义 | ★★★★★ | ★★★★ | ★★★★ | ★★★ | ★★★ |
| ② 产品设计能力 | ★★★★ | ★★★★★ | ★★★★ | ★★★ | ★★★ |
| ③ 系统架构理解 | ★★★★★ | ★★ | ★★★★ | ★★ | ★★★ |
| ④ 从0到1能力 | ★★★ | ★★★★ | ★★★★★ | ★★★ | ★★ |
| ⑤ 数据驱动决策 | ★★★ | ★★★★ | ★★★ | ★★★★★ | ★★★★★ |
| ⑥ 业务问题拆解 | ★★★★★ | ★★★ | ★★★★ | ★★★★ | ★★★★ |
| ⑦ 商业化能力 | ★★★ | ★★★★ | ★★★★ | ★★★★★ | ★★★ |
| ⑧ 增长能力 | ★★ | ★★★★★ | ★★★ | ★★★★★ | ★★★★ |
| ⑨ AI产品设计 | ★ | ★ | ★★★★★ | ★★ | ★★ |
| ⑩ AI技术理解 | ★ | ★ | ★★★★★ | ★ | ★★★ |
| ⑪ AI工具应用 | ★★ | ★★ | ★★★★ | ★★★ | ★★★ |
| ⑫ 用户研究 | ★★★ | ★★★★★ | ★★★★ | ★★★★ | ★★★ |
| ⑬ 项目管理与协作 | ★★★★★ | ★★★ | ★★★★ | ★★★ | ★★★ |
| ⑭ 自我认知与表达 | ★★★ | ★★★ | ★★★ | ★★★ | ★★★ |
| ⑮ 跨文化与本地化 | ★ | ★★ | ★★★（出海+1） | ★★ | ★ |

> 说明：★ = 1分权重，★★★★★ = 5分权重。如果用户选择"出海"标签，所有岗位的⑮维度权重+2。

### 2.2 权重的使用方式

**加权总分计算：**
```
加权总分 = Σ (维度评分 × 维度权重) / Σ 维度权重 × 100
```

**示例：Bruce面试"AI PM（出海）"**
- B端产品设计 4.0 × 4 = 16
- AI产品设计 2.0 × 5 = 10
- 跨文化与本地化 2.0 × 5 = 10
- ...
- 最终得出加权总分，反映"和目标岗位的匹配度"

## 三、评分标准（每个维度的1-5分定义）

### ① 需求分析与定义

| 分数 | 标准 | 典型表现 |
|------|------|---------|
| 1分 | 只接需求，不分析 | 收到需求直接画原型，不问为什么 |
| 2分 | 能整理需求，但缺乏深度 | 能写PRD，但需求来源主要靠别人提 |
| 3分 | 能独立挖掘需求 | 通过用户访谈/数据分析主动发现需求 |
| 4分 | 能定义需求优先级并给出依据 | 有清晰的优先级框架，能对齐业务目标 |
| 5分 | 能定义产品方向和需求体系 | 从战略层定义"做什么、不做什么"，有完整的需求管理体系 |

### ② 产品设计能力

| 分数 | 标准 | 典型表现 |
|------|------|---------|
| 1分 | 只能画简单页面 | 能用Figma/Axure画页面，但缺乏逻辑 |
| 2分 | 能设计单一流程 | 能设计一个完整的用户流程（如注册流程） |
| 3分 | 能设计多场景产品 | 考虑到异常流程、边界情况、多角色场景 |
| 4分 | 能设计复杂系统 | 多模块协同、考虑扩展性、设计模式清晰 |
| 5分 | 能定义产品架构 | 从信息架构到交互规范到设计系统，有全局视野 |

### ③ 系统架构理解

| 分数 | 标准 | 典型表现 |
|------|------|---------|
| 1分 | 不了解技术实现 | 不知道前后端区别，无法和工程师有效沟通 |
| 2分 | 了解基础概念 | 知道API、数据库、前后端的基本概念 |
| 3分 | 能理解系统间协作 | 能画出系统架构图，理解数据流向 |
| 4分 | 能参与架构决策 | 能判断技术方案的trade-off，提出合理的产品技术方案 |
| 5分 | 能主导架构设计 | 能独立设计多系统协同方案，兼顾性能、扩展性、成本 |

### ④ 从0到1能力

| 分数 | 标准 | 典型表现 |
|------|------|---------|
| 1分 | 只在成熟产品上做迭代 | 从未独立负责过新产品/新模块 |
| 2分 | 参与过从0到1 | 在团队中参与过，但不是主导者 |
| 3分 | 主导过模块级的从0到1 | 在已有平台上独立搭建过新模块（如新增一个功能模块） |
| 4分 | 主导过产品级的从0到1 | 独立负责一个产品从需求到上线到运营的全流程 |
| 5分 | 主导过商业级的从0到1 | 产品上线后有真实用户、有商业收入、有持续迭代 |

### ⑤ 数据驱动决策

| 分数 | 标准 | 典型表现 |
|------|------|---------|
| 1分 | 不看数据 | 凭直觉做决策，不关注产品数据 |
| 2分 | 事后看数据 | 做完之后看看数据，但不用数据指导决策 |
| 3分 | 能用数据发现问题 | 定期看数据面板，能从数据中发现异常 |
| 4分 | 能用数据驱动迭代 | 先看数据 → 提出假设 → 做实验 → 验证，形成闭环 |
| 5分 | 能建立数据体系 | 定义指标体系、搭建数据看板、建立A/B测试文化 |

### ⑥ 业务问题拆解

| 分数 | 标准 | 典型表现 |
|------|------|---------|
| 1分 | 只看到表面问题 | "用户流失了"就去想怎么拉回来 |
| 2分 | 能问"为什么" | 知道要分析原因，但拆解不够深 |
| 3分 | 能结构化拆解 | 用MECE、漏斗等框架把问题拆成可执行的子问题 |
| 4分 | 能定位核心卡点 | 在多个问题中识别出最关键的1-2个杠杆点 |
| 5分 | 能重新定义问题 | 发现"问的问题就错了"，从更高维度重新定义问题 |

### ⑦ 商业化能力

| 分数 | 标准 | 典型表现 |
|------|------|---------|
| 1分 | 没有商业思维 | 只关注功能和体验，不考虑怎么赚钱 |
| 2分 | 了解基础概念 | 知道SaaS/订阅/广告等变现模式，但没实操过 |
| 3分 | 参与过商业化 | 参与过定价讨论或付费功能设计 |
| 4分 | 主导过商业化 | 独立设计过产品的定价策略和付费体系 |
| 5分 | 有商业化结果 | 设计的商业模型经过市场验证，有可量化的收入数据 |

### ⑧ 增长能力

| 分数 | 标准 | 典型表现 |
|------|------|---------|
| 1分 | 不了解增长 | 不理解AARRR漏斗、不知道北极星指标 |
| 2分 | 了解增长理论 | 读过增长相关书籍/文章，能说出框架 |
| 3分 | 做过增长尝试 | 做过一些增长实验，但缺乏系统性 |
| 4分 | 有增长实战结果 | 有可量化的增长数据（用户数、转化率、留存率提升） |
| 5分 | 能建立增长体系 | 从指标定义到实验框架到团队机制，有系统性增长经验 |

### ⑨ AI产品设计

| 分数 | 标准 | 典型表现 |
|------|------|---------|
| 1分 | 不了解AI产品 | 不清楚AI能做什么、不能做什么 |
| 2分 | 给产品加过AI功能 | 在已有产品上集成AI功能（如加个AI摘要） |
| 3分 | 设计过AI辅助功能 | 设计过以AI为核心辅助手段的功能模块 |

## 四、评分流程

### 4.1 信息采集阶段

**输入方式1：简历上传**
- AI解析PDF，自动提取：工作经历、项目经验、教育背景、技能标签
- 解析后生成结构化数据，用户确认/修改

**输入方式2：引导式问答**
每段经历按以下结构采集：

```
Q1: 你在这家公司的核心职责是什么？（1-2句话）
Q2: 你负责的最重要的项目是什么？
Q3: 这个项目要解决什么问题？（业务背景）
Q4: 你具体做了什么？（你个人的决策和行动，不是团队的）
Q5: 结果是什么？（尽量给数据）
Q6: 你从这段经历中学到最重要的一件事是什么？
```

### 4.2 AI诊断阶段

**Step 1：经历拆解**
- 对每段经历提取：核心价值、能力标签、可量化结果
- 发现矛盾/盲区：用户描述 vs 简历内容是否一致

**Step 2：维度评分**
- 基于采集到的信息，按评分标准逐维度打分
- 每个评分附带评分依据（引用用户的具体经历）

**Step 3：岗位匹配**
- 根据用户选择的目标岗位，应用权重配置
- 计算加权总分和岗位匹配度

### 4.3 报告生成阶段

**报告结构：**

```
1. 总览
   - 加权总分（如：72/100）
   - 一句话总结（如："你是一个B端能力扎实的PM，正在向AI方向转型"）

2. 能力雷达图
   - 15个维度的可视化图表
   - 高亮长板（绿色）和短板（红色）

3. 长板分析（Top 3）
   - 维度名称 + 评分 + 评分依据
   - "你应该在面试/简历中重点展示这些"

4. 短板诊断（Top 3）
   - 维度名称 + 评分 + 评分依据
   - 升级式表达："你的XX能力目前是X分，如果能XX，可以提升到X分"
   - 具体提升建议（1-2个可执行的行动）

5. 经历价值挖掘
   - 你可能低估了的经历（被低估的亮点）
   - 你的经历中缺少的元素（缺数据？缺闭环？缺结果？）

6. 下一步行动
   - 基于诊断结果的3个具体行动建议
   - 引导到V2功能
```

## 五、案例演示：Bruce的评估过程

### 5.1 输入

**目标岗位：** AI PM（出海）

**经历摘要：**
- 招商银行（1.5年）：产品运营，信贷合作类贷款
- VIPKID（2.5年）：电商售后系统重构，运营策略优化
- 装小蜜（4个月）：监理业务服务完成率优化
- 超级知识产权顾问（2年）：新华网学术中国平台，成果传播模块从0到1
- AI创业（6个月）：PostMem，AI记忆产品，出海方向

### 5.2 AI诊断输出

**加权总分：58/100**（面向AI PM出海岗位）

**一句话总结：**
> 你是一个B端产品基础扎实的PM，在系统设计和业务拆解方面有明确优势。但面向AI PM出海岗位，你在C端产品、AI原生设计、商业化和增长方面存在明显短板，需要通过当前创业项目有针对性地补足。

**Top 3 长板：**
1. 业务问题拆解（4.0/5）— 装小蜜项目中把30%流失率拆解为3个可量化的归因
2. B端产品设计（4.0/5）— VIPKID售后系统涉及用户端+客服端+仓储+财务的多系统协同
3. AI工具应用（4.0/5）— 用AI完成调研、决策、原型、增长等核心PM工作

**Top 3 短板（升级式表达）：**
1. 商业化能力（1.5/5）→ "你的业务拆解能力已经是4分了，如果把同样的拆解思维用在商业模型设计上——拆解用户付费意愿、拆解竞品定价逻辑——这项能力可以快速提到3分。建议：为PostMem设计一个完整的定价方案作为练习。"
2. C端产品感觉（1.5/5）→ "你有扎实的系统设计能力，在C端领域需要补的是'用户体感'——交互细节、情感化设计、留存机制。建议：每周深度体验1个优秀C端产品，写下3个设计亮点和背后的逻辑。"
3. 自我认知与表达（1.5/5）→ "你的实际能力比你表达出来的要强。学术中国项目转化率+57%是一个很强的成果，但你对外说这段经历'没有提升'。建议：重新梳理每段经历，用'背景-行动-结果-学习'的结构重新组织，确保每段经历都讲出最大价值。"

**经历价值挖掘：**
- 被低估的亮点：学术中国项目（国家级平台、多场景从0到1、真实数据闭环）

## 六、技术实现建议

### 6.1 AI评估的核心Prompt架构

```
System Prompt:
你是一个资深的PM能力评估专家。你的任务是基于用户提供的工作经历，
按照评估框架对其进行逐维度诊断。

规则：
1. 每个评分必须基于用户的具体经历，不能凭感觉
2. 评分依据必须引用用户的原话或简历中的具体事实
3. 诊断语言使用"升级式表达"——基于长板如何补短板
4. 如果信息不足以评分，标注"信息不足"并给出追问建议
5. 主动发现用户可能低估的经历亮点

输入：
- 目标岗位：{job_type}
- 用户经历：{structured_experience}
- 评估维度和权重：{weight_config}
- 评分标准：{scoring_criteria}

输出：
- 逐维度评分 + 评分依据
- Top 3 长板分析
- Top 3 短板诊断（升级式表达）
- 经历价值挖掘
- 下一步行动建议
```
